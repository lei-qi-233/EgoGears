### Ⅰ. 段级选择题（8,033 道）— 问题最大

```
标注目录  /mnt/data/data_anno/runningbench_qa_expansion/annotations_60s/
盲猜实测  /mnt/data/data_anno/runningbench_qa_expansion/blind_test.json
规模      19 MB · 1,358 个 60 秒片段 · 来自 119 个源视频
```

#### 怎么产生的

1. 把每个源视频切成 **60 秒片段**（1,358 段）
2. 每段送 `gemini-3.1-pro-preview` 做密集描述 → `dense_annotations`
3. 用 `expand_mcq.py` 按描述出选择题，并补足干扰项

**干扰项的原始规则**（`expand_mcq.py` 的 `DISTRACTOR_PROMPT`）：

> 每个新选项必须：
> - 对这类视频**看起来合理**，长度和风格与已有选项**相似**；
> - **被证据明确否定** — 不能只是「未提及」，不能「部分正确」；
> - 与其他选项明显不同。

#### 格式分布

| 类型 | 题数 | 主体格式 |
|---|---|---|
| 单选（答案 1 个） | **4,801** | 6 选项 × 4,529；另有 4/5 选项少量 |
| 多选（答案 ≥2 个） | **3,347** | 8 选项选 3 个 × 1,117；8 选 4 × 838；8 选 2 × 583 |

#### 已实测的问题 ⚠️

**在 801 道分层抽样上，用同一个模型做「不给视频、只给题干和选项、答三次」的盲猜测试：**

| | 可猜率（≥2/3 次命中） | 95% CI |
|---|---|---|
| 单选 | **64.7%** | — |
| 多选 | **25.3%** | — |
| **整体** | **48.6%** | **[45.1, 52.0]** |

其中 **41.6% 的题三次全中** —— 那不是运气，是题目本身泄漏。
外推到全库约 **3,772 道不看视频就能答对**。

> **重要更正**：此前项目内引用的「17.6%」是**字母分布的恒答上限**
> （即「永远选 C」能得多少分），不是盲猜率。两者差了近 3 倍，
> 之前用 17.6% 汇报过，是错的。

#### 泄漏的两个具体机制（我逐题看出来的）

**机制 A：正确项是最具体、最长的那个。**

```
Q: 远处路的右侧有哪些具体物体？
   A. 一个保安亭和一个金属自行车架
   B. 一辆黄色校车和一条水泥长椅
   C. 一个蓝色邮筒和一堆木托盘
   D. 一辆红色自行车和一个绿色回收桶
   E. 一辆摩托车和一堆建筑碎石
   F. 停放车辆中的一辆白色面包车，以及一个深色大垃圾箱   ← 正确
```

干扰项是通用物件，正确项是「真的被观察到的东西」，更长更具体。

**这个机制我做了量化验证**：策略「挑最长的 k 个选项」的命中率 ——

| | 命中率 | 95% CI |
|---|---|---|
| 单选 | **42.2%** | [40.9, 43.6] |
| 多选 | 5.5% | [4.7, 6.3] |

**长度泄漏是单选题特有的**，对多选几乎无效（因为「挑最长的 3 个」很难正好命中一个集合）。

**机制 B：干扰项在常识上不可能。**

```
Q: 什么听觉和体感线索表明拍摄者的移动方式？
   A. 沉重的引擎噪音和震动的仪表盘视角
   B. 自行车齿轮的咔哒声和摆动的车把
   C. 缓慢拖沓的脚步、长时间停顿、镜头无起伏
   D. 完全静音，画面完美稳定平滑滑行
   E. 大风呼啸伴随突然剧烈的镜头跳动
   F. 有节奏的镜头晃动，伴随脚步声和呼吸声   ← 正确
```

只要知道「这是第一人称跑步视频」，A、B、D 立刻排除 —— 不用看画面。

**根因**：原始规则只要求干扰项「被证据否定」。**「被否定」保证选项是错的，
不保证选项有吸引力。** 这是整套段级语料的设计缺陷。

#### 正在做的修复（进行中）

只修 **3,347 道多选题**，不修 4,801 道单选题。

```
脚本  /mnt/task_runtime/bolt/gdrive_relay/repair_segment_distractors.py
命令  --all --multi-only --no-blind --jobs 6
产出  /mnt/data/data_anno/runningbench_segment_repair/repaired_multi.json
进度  399/3347（约 12%），预计还需 5 小时
```

**为什么放弃单选**：小试点（n=60）显示修复后单选仍有 54.5%，多选降到 21.1%。
单选有两个叠加泄漏（长度 42% + 语义），修一个还剩一个。

**为什么这个数字不能全信**：n=60 太小，三个区间全部与修复前重叠。
要以 80% 效力分辨 48.6% vs 41.7%，每组需约 **816 道**。**修复效果尚未被证实。**

#### 修复过程中踩的一个坑（务必理解）

第一版修复规则是「干扰项 = 正确项改一处」（near-miss）。结果盲猜率**从 48.6% 升到 75%**。

原因是数学上必然的：如果每个干扰项都是正确项改一个属性，
**正确项就是所有选项在每个维度上的众数**：

```
A. 深灰色   · 多层 · 大玻璃
B. 浅黄色   · 多层 · 大玻璃    ← 正确，且在每个维度上都是多数
C. 浅黄色   · 单层 · 大玻璃
D. 深红色   · 多层 · 大玻璃
E. 浅黄色   · 多层 · 小窄木窗
F. 浅黄色   · 多层 · 极小窗
```

颜色取「浅黄色」（4 票）、层数取「多层」（5 票）、窗户取「大玻璃」（4 票）—— 逐维度投票即可还原答案。

**更值得警惕的是**：我想修的那个指标确实修好了（「正确项最长」从 48% 降到 28%），
**只看那个指标会以为成功了，只有盲猜实测暴露了真相。**

现在的规则改成：多数干扰项同时改两处以上、不同选项改不同组合、
正确项的任何细节不得出现在半数以上选项、干扰项之间也要互为近似。

### Ⅲ. 完整视频线（1,758 道生成 / 793 道通过）— 质量最高

```
脚本  /mnt/task_runtime/bolt/gdrive_relay/build_fullvideo_annotations.py  (781 行)
产出  /mnt/data/data_anno/runningbench_fullvideo/<route_id>/
规模  29 GB（含模型输入视频）
```

**评测单元是完整原始视频**，不切片。60/180 秒窗口只作为内部时间索引存在。

#### 五步流程

```
1. GLOBAL PASS   整段视频，360p/10fps（≤11 MiB，超了降 288p）→ gemini-3.1-pro-preview
                 产出 route_phases / turns / return_to_start / revisited landmarks /
                       environment stages / dynamic events
                 —— 粗但完整：要的是顺序和结构

2. TIME INDEX    已有的 3 分钟窗口观察合并进来作为 time_index
                 —— 只为证据提供更细的时间戳，绝不作为样本

3. WHOLE-VIDEO 出题   每个 run 用自己的标注出题
4. CROSS-VIDEO 出题   每条 route 用该 route 全部 run 的标注出题

5. GATES（闸门，见下）
```

超过 **900 秒**的视频会被切成两半分别标注，再用 `MERGE_PROMPT` 调和 ——
因为单个内联文件再长下去码率会掉到 70 kbps 以下。

#### 闸门顺序（这是全项目最重要的一段）

```
① shuffle_options       确定性打乱（题干 SHA-256 做种）
② structure             结构校验
③ leak_scan             黑名单词扫描
④ blind_guess ×3        不给视频答三次，≥2 次命中 → 淘汰
⑤ visual_recheck        480p 高清片段，按 evidence_spans 精确切出，问画面是否支持答案
```

**顺序不可颠倒，且 ④ 必须在 ⑤ 之前**：④ 命中的题直接标 `skipped` 不再走 ⑤，
省掉最贵的视频调用。

**`leak_scan` 黑名单**（代码里的 `LEAK` 常量）：

```
"fast", "slow", "normal speed", "trial", "traj", ".mov", ".mp4",
"filename", "described", "the evidence", ...
```

防的是题干里泄漏文件名、拍摄速度、或「根据描述…」这类把标注本身当线索的措辞。

**`OUT_OF_SCENE` 黑名单**：

```
"beach", "highway", "motorway", "forest", "woods", "indoor",
"track", "boardwalk", "figure-eight", ...
```

防的是干扰项引入这个场景根本不可能有的东西 —— 也就是段级语料的「机制 B」。
**完整视频线有这道防线，段级语料没有。**

#### 一个刻意的分辨率决定

```
GLOBAL PASS   288p / 8 fps   —— 够看路线结构（顺序、阶段、转弯）
visual_recheck 480p          —— 细节复核要更清晰
```

**为什么回看要 480p**：曾用 360p 做回看，模型把一块清晰可读的路牌误判成「模糊」，
产生了假的 `contradicted`。**降分辨率会制造假阴性。**

### Ⅳ. 完整视频 摘录（119 道生成 / 65 道通过）

```
产出  /mnt/data/data_anno/runningbench_excerpts/
报告  /mnt/data/data_anno/runningbench_excerpts/EXCERPT_REPORT.md
规模  10 GB
```

目的：填平时长分布 —— 主语料几乎全是 7 分钟以上的长视频，缺短时长样本。

从源视频剪出 **22 段摘录**，四个时长档，走与主语料**完全相同**的五步流程。

| 档位 | 可用/生成 | 产出率 | 95% CI |
|---|---|---|---|
| 1min | 15/36 | 42% | [27, 58] |
| 2min | 18/34 | 53% | [37, 69] |
| 4min | 18/30 | 60% | [42, 75] |
| 7min | 18/30 | 60% | [42, 75] |
| **合计** | **69/130** | **53%** | **[45, 61]** |

时长分布填平后：1 分钟档 5→11 个、2 分钟档 13→19、4 分钟档 5→10、7 分钟档 30→35。

#### 一条否定结果（重要）

摘录码率 **215–1502 kbps**，主语料 **45–146 kbps**，差 10–30 倍。假设是「提高输入画质能提高产量」。

**结果不支持这个假设：**

| | 摘录 | 主语料 |
|---|---|---|
| 回看矛盾（画质相关的失败） | 17% | 26% |
| **盲猜可猜（选项构造的失败）** | **29%** | **29%** |

画质确实改善了回看矛盾，但**盲猜损耗纹丝不动**。
**产量瓶颈在干扰项构造，不在输入质量。**

#### 一条我必须收回的说法

跑批过程中我报过「产出率随时长单调上升」和「4 分钟见顶（倒 U 形）」。
**加上置信区间后两个说法都站不住** —— 1min 的 [27,58] 与 4min 的 [42,75] 重叠，
4min 与 7min 区间完全重合。每档只有 30–36 道题，分辨不出 20 个百分点以内的差异。
**那些播报是过度解读。**

### 一条反直觉的运维教训

把 `maxOutputTokens` 从 8192 降到 2048，**耗时从 10.7 秒涨到 38.5 秒**并触发两次重试。

**思考 token 从输出预算里扣** —— 预算给小了，思考把正文挤掉，返回不完整 JSON，
校验失败重试。**降 token 省不了钱，反而更贵。**

### 并发的实际约束

单次重造调用约 **10.7 秒**，所以单线程只有 0.13 req/s，配额给的是 0.45。
**瓶颈是延迟，不是配额。** 3 线程 → 6 线程把吞吐从 3.9 提到 8.3 道/分钟。

但线程数翻倍**不等于**吞吐翻倍（实测 0.200 → 0.287 req/s）。
我连续三次线性外推都偏乐观（4.6h → 14h → 6.2h → 5.2h），**别信线性外推。**

6 线程时开始出现零星 429，脚本有 12 次指数退避重试可自愈。

## 5. 人工筛选操作规范

**要做的事一句话**：把 9,925 道「状态未知」的题，逐题判定成「能用」或「不能用」。

判定标准只有一条：

> **不看视频能答对的题，不能用。** 无论文字多漂亮、答案多正确。

---

### 5.0 为什么必须逐题判定

段级那 8,033 道我们**抽样测过**：801 道（9.8%）里有 389 道不看视频就能答对，
即 48.6%（95% CI [45.1, 52.0]）。外推全库约 3,900 道有问题。

**但我们不知道是哪 3,900 道。** 抽样只给出比例，不给出名单。
所以现在这 8,033 道混在一起，无法使用 —— 用了分数会虚高，
而虚高的部分不是模型真的看懂了。

**逐题判定是唯一出路**，没有捷径。

---

### 5.1 P0 · 段级 60 秒题 8,033 道（最高优先）

#### 你需要什么

```
题目      /mnt/data/data_anno/runningbench_qa_expansion/annotations_60s/**/*.json
          每个文件的 qa_pairs 字段
视频片段  /mnt/data/data_anno/runningbench_segment_repair/clips_480p/
          1,332 段 60 秒 480p 片段，按源视频分目录
          文件名 <video>_segment_<N>.480p.mp4，对得上标注里的 segment_index
```

#### 流程：每道题走三步

**第一步 · 打乱选项**

如果你要重新排列选项顺序，**必须在第二步之前做完**。

> ⚠️ 生成器习惯把正确答案放在前面，答题者也习惯选前面的。
> 打乱前测盲猜会得到虚高读数 —— 我们曾在完整视频线上测出 56.6%，
> 后来发现那是位置造成的假象，真实值低得多。

段级题的 `option_order` 字段已标记为 `shuffled`，如不重排可跳过此步。

**第二步 · 盲猜测试（决定性的一步）**

**盖住视频，只看题干和选项，答三遍。**

| 三遍结果 | 判定 |
|---|---|
| 答对 ≥2 遍 | ❌ **淘汰** —— 记为 `blind_guessable` |
| 答对 ≤1 遍 | ✅ 进入第三步 |

**为什么答三遍**：区分「运气」和「真泄漏」。6 选 1 蒙对一次的概率 16.7%，
连中两次是 2.8% —— 不太可能是偶然。

**谁来做**：找没出过这批题的人做效果最好。自己出的题自己盲猜会带入记忆。
只能自己做的话，出完题隔一天再测。

**用模型代做也可以** —— 我们的自动闸门就是用模型做的，提示词是：

```
Answer this multiple-choice question WITHOUT any video — you have none.
QUESTION: {question}
OPTIONS: {options}
Exactly one option is correct.  (attempt 1)
Return only JSON: {"answer": ["..."]}
```

参考脚本：`/mnt/task_runtime/bolt/gdrive_relay/blind_test_segments.py`（140 行）

**第三步 · 看视频复核**

**用 480p 片段**（不要更低），对着画面逐项检查：

- 标记为正确的选项，画面是否**真的**支持？
- 标记为错误的选项，画面是否**真的**否定？

| 结果 | 处理 |
|---|---|
| 画面支持标记的答案 | ✅ **通过，可用** |
| 画面显示的是别的 | ❌ 淘汰，记为 `contradicted`，**并写下画面实际是什么** |
| 画面看不清判不了 | ❌ 淘汰，记为 `insufficient` |

> ⚠️ **复核必须用 480p 或更高。** 我们曾用 360p，模型把一块清晰可读的路牌
> 误判成「模糊」，于是废掉了一道正确的题。**降分辨率会制造假阴性。**

#### 顺序不能颠倒

```
打乱 → 盲猜 → 看视频
```

**盲猜必须在看视频之前** —— 盲猜淘汰的题不用再看视频，
省掉整个流程最贵的一步（我们的自动闸门靠这个省了约 20% 的视频调用）。

#### 优先处理这些片段（性价比最高）

**① 74 个不足 55 秒的尾片，特别是 9 个不足 10 秒的**

```
最短三个:  1.27 秒 · 1.32 秒 · 1.39 秒
次短一批:  5.62 · 5.82 · 6.47 · 7.31 · 7.77 · 8.57 秒
```

**这三个 1 秒多的片段各自也交了 6 道题。** 1.27 秒约 38 帧，几乎是一张静止图 ——
出不了 6 道需要看视频的题。**这 18 道题基本可判定是凑的。**

先查这 9 个片段的 54 道题。如果它们看起来都「正常」，
说明生成器在**编造画面内容**，问题比可猜率显示的更严重。

**② 单选题优先于多选题**

实测差距是压倒性的：

| | 可猜率 |
|---|---|
| 单选（4,672 道） | **64.7%** |
| 多选（3,361 道） | **25.3%** |

单选题里约三分之二有问题，多选题里约四分之一。**先筛单选。**

---

### 5.2 P1 · Video Bench 1,892 道

**这是全库最大的未知 —— 从未做过盲猜实测。**

它的 `blind_ceiling: 33.2` 是**恒答上限**（「永远选 C」能得多少分），
不是实测盲猜率。段级语料在同一个错误上差了近 3 倍：

```
标称 17.6%（恒答上限）  vs  实测 48.6%（真盲猜）
```

#### 该做什么

**分层抽样 800 道做盲猜实测**，按 `answer_format × family` 分层。
800 是算出来的：要以 80% 效力分辨 7 个百分点的差异，每组约需 816 道。

**特别注意两类：**

**① 444 道「2 选项」题** —— 二选一随机基线就是 50%，盲猜天然占优。
这类题即使实测 50% 也说明不了什么，需要单独看。

**② numeric 题（1,017 道，未计入 11,802）** —— 问「有几条铁丝」这类，
答案集中在 1-4 的小整数，常识先验极强。建议单独分层统计。

---

### 5.3 P2 · 抽查已通过的 793 道

**闸门是自动的，需要人验证闸门本身。**

分层随机抽 **120 道**（按题型比例），人工独立作答后对照。

每道题记录三件事：

| 记录项 | 判断标准 |
|---|---|
| **不看视频能答对吗？** | 答对了 → 盲猜闸门漏了 |
| **看了视频答案对吗？** | 标注的 `answer` 是否真的正确 |
| **题干有歧义吗？** | 是否有第二个选项也说得通 |

**关键对照**：每道题的 `gates.blind_guess.hits_of_3` 记录了模型三次盲猜的结果。
**如果人能猜对但模型 `hits_of_3=0`，说明人类和模型的先验不同** ——
那是个真问题，意味着盲猜闸门有系统性盲区。

---

### 5.4 P3 · 反查已淘汰的 1,084 道

从这批里抽 **40 道**，看闸门是不是杀错了。

```
盲猜可答      542    题目泄漏（答案可能是对的，只是选项好猜）
回看矛盾      478    真值错了
证据不足       64    画面判不了
```

**重点看 `contradicted` 那 478 道** —— 回看用 480p，但如果画面确实模糊，
模型仍可能误判。每道题的 `gates.visual_recheck.notes` 有模型的理由。

**两种淘汰性质不同**：

- **盲猜可答** = 题出得不好，重造干扰项还能救
- **回看矛盾** = 答案是错的，要改答案或废掉

---

### 5.5 记录格式

每道判定过的题追加一个 `human_checks` 字段：

```json
"human_checks": {
  "annotator": "你的标识",
  "date": "2026-09-01",
  "shuffled": true,
  "blind_test": {
    "attempts": [["A","C","F"], ["B","D","G"], ["A","E","H"]],
    "hits_of_3": 0
  },
  "visual_recheck": {
    "verdict": "supported",
    "notes": "画面在 0:12 显示白色面包车停在深色垃圾箱左侧"
  },
  "final": "usable"
}
```

`final` 取四个值之一：

```
usable              通过，可用
blind_guessable     盲猜淘汰
contradicted        真值错误
insufficient        画面判不了
```

**`human_checks` 必填。** 没有自检记录的题无法验收 ——
我们无法区分「测过且通过」和「没测」。

---

### 5.6 验收门槛

```
1. 随机抽 10% 复核盲猜 → 判为 usable 的题里，可猜率必须低于 15%
2. 随机抽 10% 复核答案 → 正确率必须高于 90%
3. human_checks 字段完整性 → 缺失即退回
4. 答案位置分布 → 均匀，无某位置占比过高
5. 同类题答案内容分布 → 无某答案压倒性多数
```

**第 1 条是硬门槛。** 现有段级语料是 48.6%，目标是 15% 以下。

---

### 5.7 遇到边界情况怎么判

**判断标准**：你能想出一个**不看视频**的理由来选它吗？能，就是可猜。

常见的「不看视频的理由」：

| 理由 | 例子 |
|---|---|
| 这个选项最长、最具体 | 实测单选题「挑最长的」命中 42.2% |
| 其余选项在常识上不可能 | 跑步视频里不会有「引擎轰鸣」「仪表盘视角」 |
| 这个选项是各维度的众数 | 五个干扰项都只改一处 → 正确项成为逐栏多数 |
| 这个选项读起来最连贯 | 其余选项像编的 |

**四条都要查。** 第三条最隐蔽 —— 详见 §2.Ⅰ 里那个把盲猜率
从 48.6% 推到 75% 的真实案例。

## 6. 已知的方法论陷阱清单

给人工校准员的「别踩」列表，每条都是实际踩过的。

| # | 陷阱 | 后果 | 怎么避 |
|---|---|---|---|
| 1 | 把**恒答上限**当盲猜率 | 段级 17.6% vs 实测 48.6%，差 3 倍 | 必须实际跑模型盲猜，不能算字母分布 |

| 3 | 干扰项「改一处」 | 正确项成为逐维度众数，盲猜率升到 75% | 多处同改、不同组合、正确项细节不得过半 |
| 4 | 只看**代理指标** | 「正确项最长」修好了（48%→28%）但盲猜率反升 | 代理指标不能替代盲猜实测 |

| 6 | 降 `maxOutputTokens` 省钱 | 10.7s → 38.5s 且触发重试 | 思考 token 从输出预算扣，给小了更贵 |
| 7 | 回看用低分辨率 | 360p 把清晰路牌误判成「糊」，产生假阴性 | 回看用 480p，比全局标注更清晰 |
| 8 | 线性外推耗时 | 连续三次估错（4.6→14→6.2→5.2 小时） | 延迟不随线程数线性下降 |
| 9 | 闸门顺序颠倒 | 盲猜应在回看前，否则白烧最贵的视频调用 | ①打乱 ②结构 ③黑名单 ④盲猜 ⑤回看 |
| 10 | 多选题用长度指标 | 长度策略在多选上只有 5.5% 命中，指标无意义 | 长度泄漏是**单选特有**的 |

## 10. 60秒切片双模型自动标注流水线 (Dual-Model Annotation Pipeline)

基于主库的 60 秒片段，我们使用了一个全自动的双模型（Dual-Model LLM）流水线来生成高质量的多模态问答。该流程全部在 Apple Bolt H100 8-GPU 集群上自动化完成。

### 10.1 物理层：切片与自适应压缩 (Video Segmentation)
- **切片**：通过 `ffmpeg`，将原始的长视频精准切割为 60 秒的标准原子片段（Chunk）。
- **自适应压缩**：由于 Floodgate Gemini 接口严格的 20MB Base64 载荷限制，大于 12MB 的切片会被自适应降采样和压缩（H.264 + AAC, 480p, crf 34），以确保符合限制。

### 10.2 感知层：Dense Captioning (gemini-3.1-pro-preview)
每个 60 秒切片会被传入 Gemini 3.1 Pro 视觉大模型以生成细粒度的自然语言描述，包含 **5个核心维度**：
1. **整体环境 (Overall Environment)**：光照、天气、时间、环境上下文。
2. **物体与属性 (Objects and Attributes)**：建筑物、道路设施、行人、车辆及其外观。
3. **动作与事件 (Actions and Events)**：录制者的运动序列、路过的地标。
4. **空间关系 (Spatial Relations)**：物体相较于运动路径的左右分布及相对位置。
5. **轨迹与转向 (Trajectory and Turnings)**：移动轨迹特征（直行、左转、右转、环形等）。

*执行脚本：`batch_annotate_videos.py`*

### 10.3 认知层：JSON 结构化与 MCQ 生成 (gemini-3.5-flash)
利用 Gemini 3.5 Flash 充当考官，将冗长的原始长文本转换为测评问答：
- **JSON 结构化转换**：提取并固化为 `dense_annotations` 字段。
- **题目生成**：每段视频精准产出 **3 道高质量选择题（MCQ）**。
- **题目约束**：
  - **强制混合单选和多选**（以防猜测和分布漏洞，增加 Bench 难度）。
  - **覆盖三大认知维度**：
    - `trajectory-qa`（轨迹与路线推理）
    - `visual-grounded-qa`（视觉细节与物体属性定位）
    - `spatial-temporal-reasoning`（时空与相对空间推演）

*执行脚本：`convert_to_mcq_json.py`*

### 10.4 评估层：VLM Benchmark Inference
这批产出的 QA 数据被送入 Qwen 系列模型（如 Qwen2.5-VL-7B-Instruct, Qwen3-VL-8B-Instruct）进行自动化闭环评测，采用严格的 Exact Match 评分策略（多选题不给部分分）。
